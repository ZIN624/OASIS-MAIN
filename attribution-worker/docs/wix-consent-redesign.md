# Wix の広告クリックの受け取りと、LINE 入口の同意の改修案（2026-10-22）

> **これは案です。コード・Wix・LINE の設定は、まだ何も変えていません。**
> 法律の扱いは、どれも弁護士の確認が要ります（下の「プライバシー対応が必要な箇所」）。
> 条文の番号は書いていません。記憶で書かないためです。

## 1. いまの流れ（コードを読んで確かめたもの）

| 時点 | どこで | 何が起きるか | 同意は |
|---|---|---|---|
| ① 広告から本店のページを開く | Wix（`wix/honten-ad-entry.html`） | URL の gclid / gbraid / wbraid を読み、**その場で Worker に送る**（`POST /v1/ad-click`） | **まだ** |
| ② Worker が受け取る | Worker | クリック識別子と utm を `ad_clicks` に保存する。`ad_ref`（乱数）を返す | まだ |
| ③ LINE ボタンを押す | Wix | 行き先を入口ページ（`liff.line.me/<入口>?ad_ref=…`）に書き換えてある | まだ |
| ④ 入口ページ | `entry.html` / `js/entry.js` | LINE のログイン画面（LINE の許可画面）→ こちらの説明と2つのボタン | ここで初めて聞く |
| ⑤a 同意する | 入口 → Worker | IDトークンと `ad_ref` を送って結ぶ（`POST /v1/bind`） | 同意あり |
| ⑤b 同意しない | 入口 | Worker には何も送らない。LINE へ進む | 同意なし |
| ⑥ 結ばれなかったクリック | Worker（毎日 JST 4:00） | 結びつけの期限（24時間）を過ぎたら消す | — |

### 問題

1. **同意の前に、クリック識別子がサーバに届く（①②）。** ページを開いただけの人、LINE ボタンを押さない人のぶんも届く
2. **同意しなかった人のクリックも、すぐには消えない（⑤b → ⑥）。** 消えるのは期限の24時間のあと、さらに毎日1回の削除を待つので、**最長で約48時間**サーバに残る
3. **Wix の同意設定は「広告を拒否した」ときだけ止まる。** バナーを出していない・読み込みが間に合わない（`consentPolicyManager` がまだ無い）ときは、送る側に倒れる
4. **入口の説明文は「同意いただいた場合に限り結びつける」と書いている。** 結びつけについては正しいが、①②で識別子をすでに受け取っていることは書いていない
5. **予約フォームを開いた人は全員、IDトークンを Worker と LINE で確かめている**（`js/attribution.js` の `startSession`）。広告から来ていない人も対象。保存はしないが、扱いはしている

## 2. 案

### 案A: いまのまま（文面だけ直す）

- 変更は文面だけ
- 問題1〜3は残る

### 案B: LINE ボタンを押したときに送り、押すのを待ってから進む

- ① ではクリック識別子をページの中（メモリ）に持つだけ。サーバにも端末の保存領域にも置かない
- ボタンを押したら `POST /v1/ad-click` を送り、`ad_ref` が返ってから入口ページへ進む（最大1.5秒。間に合わなければ、いつもの LINE へ）
- 弱いところ
  - 押してから進むまで待たせる
  - **Wix の LINE ボタンが新しいタブで開く設定（`target=_blank`）だと、待ったあとに開くとブラウザに止められる**ことがある。いまの設定は未確認

### 案C（推奨）: 押したときに送り、待たずに進む

- ① ではクリック識別子をページの中に持つだけ（案Bと同じ）
- ボタンを押したら、**ブラウザの中で `ad_ref`（128ビットの乱数）を作る**
  - その場で入口ページ（`?ad_ref=…`）へ進む
  - 同時に、ページを離れても届く送り方（`fetch` の `keepalive`）で `POST /v1/ad-click` を送る
- 待ち時間が無いので、新しいタブで開く設定でも止められない
- 入口ページの結びつけは、クリックの記録がまだ届いていなければ（404）、短く2〜3回だけやり直す
- サーバの変更
  1. `POST /v1/ad-click` が、ブラウザが作った `ad_ref` を受け取れるようにする。形は22文字の base64url。すでにあれば 409。サーバの乱数で作り直さない
  2. **同意しなかったときに、そのクリックをすぐ消す口を足す**（`POST /v1/decline`。`ad_ref` だけを受け取り、結ばれていなければ消す）
  3. 結ばれなかったクリックの削除を、毎日1回から毎時に変える（いまの毎時の定期実行に相乗りする。定期実行は増やさない）
  4. 結びつけの期限を24時間から短くするかどうか（例: 2時間）は、オーナーの判断（下の「決めること」）
- `ad_ref` をブラウザで作っても安全な理由
  - 乱数を知っているのは、その人のブラウザだけ
  - 他人がその番号を当てることはできない（128ビット）
  - 偽の番号で自分のクリックを作れるのは、いまの仕組みでも同じ（クリックの登録は誰でも呼べる）

### くらべ

| | 案A | 案B | 案C |
|---|---|---|---|
| ページを開いただけで届く | 届く | 届かない | 届かない |
| 同意しなかった人のクリック | 最長約48時間残る | 最長約48時間残る（削除の口を足せば即時） | 即時に消える |
| 押してからの待ち | なし | 最大1.5秒 | なし |
| 新しいタブの設定で止められる | なし | ありうる | なし |
| 変えるところ | 文面 | Wix・文面 | Wix・入口・Worker・文面 |
| 計測できる数 | いまと同じ | ほぼ同じ（待ちきれずに離れた人は減る） | いまと同じ |

### 残る点（どの案でも）

- 同意を聞く前に、ボタンを押した人のクリック識別子はサーバに一度届く（入口ページで `ad_ref` と結ぶため）
  - これを無くすには、Wix のページの上で先に同意を聞くしかない。その場合は、決定②（LINE ログインの同意は広告から来た人だけ）の形が変わる
- **クリック識別子を LINE の URL に載せる案は採らない。** LINE（第三者）に識別子が渡るため

## 3. 予約フォームでの IDトークンの確認（問題5）

| | いま | 案D: 印があるときだけ確かめる |
|---|---|---|
| 確かめる人 | フォームを開いた全員 | 入口ページで同意した人だけ |
| しくみ | — | 同意したら、入口ページが端末に印を置く（識別子は入れない。日付だけ。90日） |
| 弱いところ | 広告と無関係な人の扱いがある | 端末の保存が消えた・別の端末から送った、だと計測から漏れる |

入口ページと予約フォームは同じ場所（`zin624.github.io`）にあるので、印は共有できるはずです。
**ただし、LINE アプリの中のブラウザで本当に共有されるかは未確認です。** 実機で確かめてから決めます。
